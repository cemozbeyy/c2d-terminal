How to review Claude Code's changes before you commit

Claude Code edits files fast. The safe habit is simple: let it change the working tree, then read the diff and make the commit yourself. This guide shows how to set that up in any terminal, and how C2D Terminal makes it the default.

Updated 29 October 2026 · Written by the makers of C2D Terminal

1. Stop Claude Code from committing on its own

Claude Code reads permission rules from .claude/settings.json in your project (shared with the team) or ~/.claude/settings.json (just you). An ask rule makes Claude Code stop and ask you before a matching command runs:

{
  "permissions": {
    "ask": [
      "Bash(git commit *)",
      "Bash(git push *)"
    ]
  }
}

Use deny instead of ask if you never want Claude Code to run them. Claude Code checks deny rules first, then ask, then allow, so a deny or ask rule wins over any allow rule that also matches.

Three things that catch people out:

  • An earlier "Yes, and don't ask again". If you once approved git commit that way, Claude Code saved an allow rule to .claude/settings.local.json at the repository root. Your new ask or deny rule still wins, but delete the old entry so the file says what you mean.
  • Rules match the command as written. Bash(git push *) does not catch a push written another way, such as git -C . push. Treat rules as a guard rail, not a lock.
  • CLAUDE.md is an instruction, not enforcement. A line such as "Never commit or push. Stop after the change and tell me what to review." helps, and Claude Code reads it every session, but only permission rules make it stop and ask.

2. Read the whole diff, not the summary

When Claude Code says it is done, its summary is a claim. The diff is the evidence. In a second terminal:

git status            # which files changed, and any new untracked files
git diff              # every unstaged change, line by line
git diff --stat       # a quick size check: did it touch more than you asked?

Look for files you did not expect, deleted tests, loosened assertions, and new dependencies. Untracked files do not show up in git diff, so check git status for them.

3. Stage hunk by hunk

Agents often bundle a good change with an unrelated one. Stage only what you have read and agree with:

git add -p            # walk through each hunk: y to stage, n to skip, s to split
git diff --staged     # exactly what the commit will contain

Anything you skip stays in the working tree, so you can ask Claude Code to rework it or throw it away with git restore <file>.

4. Run the tests, then commit

Run the project's tests yourself before you commit, even if Claude Code already said they pass. Then write the commit, or ask Claude Code to draft the message and paste it in. The commit is yours either way.

Doing the same in C2D Terminal

C2D Terminal is built around this loop. Claude Code runs in a real terminal inside the app, and every file it touches shows up in the Git panel next to it:

  • Status and diff for every changed file. Diffs open as an editor tab.
  • Stage and unstage per file or per hunk, without leaving the window.
  • Commit, optionally with a message drafted by Claude Code.
  • Fetch, Pull and Push are separate buttons. The app itself never commits, pushes, pulls or discards on its own.
  • Run the tests in a terminal pane in the same window, next to the diff.

One thing C2D does not do: it does not stop Claude Code from running git commit in its own terminal. C2D runs the unmodified claude CLI and leaves its permission settings to you, so add the rules from step 1 if you want Claude Code to ask first.
